# app-shell Specification

## Purpose
Оболочка приложения обеспечивает запуск сайта, восстановление доступной сессии и переходы между каталогом, входом и регистрацией без повторной загрузки документа.

## Requirements

### Requirement: Общий футер
Каталог, вход и регистрация SHALL показывать внизу страницы общий белый футер с логотипом VibeMarket, копирайтом и адресом поддержки.

#### Scenario: Переход между экранами
- **WHEN** пользователь открывает каталог, вход или регистрацию
- **THEN** видит одинаковый футер с работающей ссылкой на каталог и адресом поддержки.

### Requirement: Запуск приложения
После успешной загрузки шаблонов и попытки восстановить сессию приложение SHALL показывать каталог. При ошибке загрузки шаблонов SHALL отображаться понятное сообщение вместо пустого экрана.

#### Scenario: Первое открытие
- **WHEN** пользователь открывает сайт и ресурсы доступны
- **THEN** после попытки восстановить сессию отображается каталог.

#### Scenario: Недоступный шаблон
- **WHEN** один из шаблонов не удаётся загрузить
- **THEN** появляется сообщение о невозможности загрузить приложение с предложением обновить страницу.

### Requirement: Переключение экранов
Переходы между каталогом, входом и регистрацией SHALL выполняться без перезагрузки документа и изменения URL. После обновления браузера SHALL открываться каталог.

#### Scenario: Возврат из формы
- **WHEN** пользователь нажимает на логотип в форме входа или регистрации
- **THEN** каталог заменяет форму без перезагрузки страницы.

### Requirement: Ресурсы интерфейса
Приложение SHALL загружать библиотеку шаблонов, шрифты, стили и скрипты со своего HTTP-сервера без обращения к сторонним CDN. Адреса фотографий товаров SHALL браться из ответа API.

#### Scenario: Открытие после установки зависимостей
- **WHEN** пользователь открывает подготовленный сайт
- **THEN** ресурсы интерфейса загружаются с адреса сайта, а фотографии товаров — по адресам из API.

### Requirement: Локальная разработка с API
Frontend SHALL запускаться через `npm start` на `http://localhost:8081`. Локальный Node.js-сервер SHALL раздавать содержимое `public/` и проксировать запросы `/api/*` на отдельно запущенный backend `http://localhost:8080`. Frontend SHALL использовать относительный API-префикс `/api/v1`, чтобы браузер отправлял API-запросы на origin frontend. CORS для этой same-origin схемы SHALL NOT требоваться.

#### Scenario: Запрос к API при локальном запуске
- **WHEN** frontend запущен на `http://localhost:8081` и браузер запрашивает `/api/v1/products`
- **THEN** браузер отправляет запрос на origin frontend, а локальный сервер проксирует его на `http://localhost:8080/api/v1/products` без необходимости CORS.

### Requirement: Production-развёртывание
Production-сборка через Vite и `dist/` SHALL NOT требоваться. HTTP-сервер SHALL раздавать подготовленное содержимое `public/` и проксировать `/api/*` на production-backend. Конкретная реализация reverse proxy SHALL NOT требовать именно nginx.

#### Scenario: Публикация frontend
- **WHEN** frontend развёрнут в production и браузер запрашивает `/api/v1/products`
- **THEN** HTTP-сервер отдаёт frontend из `public/` и проксирует API-запрос на production-backend под тем же origin.
